## 0. 为什么要有这份规格

组里四个人写代码、两个人看图，最容易出的事是**同一条报表两套口径**（"活跃客户"按人还是按次、金额算不算未结算、
工单算不算没匹配上身份的）。这份文件把每条报表的**粒度、口径、过滤条件、已知限制**写死；
报告正文、演示口播、dashboard 三处必须引用同一份口径，数字对不上就来找这里。

三条硬规则（来自契约 §6，也是评分点最容易失分的地方）：

1. **报表只读集成仓库 `dw.*`**，不直连 `s1_core` / `s2_payments` / `s3_digital`。
2. **每个 fact 先各自聚合，再 join**（`10_report_views.sql` 里每个 CTE 只碰一张事实表）。
   直接 join 三张事实表有两种失败方式，本 fixture 两种都验证过（测试 T11a / T11b）。
3. **不给数据没有的维度编归属**。`fact_service_case` 没有 `channel_key`，所以工单**不按渠道报**（测试 T10）。

## 2. 逐条口径

### R1 Customer 360 —— `dw.v_r1_customer_360`
| 列 | 定义 | 口径说明 |
|---|---|---|
| `customer_key`, `full_name` | 仓库客户 | 来自 `dim_customer`，跨 S1/S2/S3 合并后的实体 |
| `match_quality` | `EXACT_ID` / `EMAIL_MATCH` / `SINGLE_SOURCE` | 该客户身份是怎么定下来的（**报告里要能解释**） |
| `accounts` | `count(dim_account)` | 按 `customer_key` 聚合 |
| `transactions` / `amount_aud` | `count` / `sum(fact_transaction.amount_aud)` | **只含身份已解析（`customer_key IS NOT NULL`）的交易** |
| `digital_activities` | `count(fact_activity)` | 同上 |
| `service_cases` / `open_cases` | `count` / `count(status='OPEN')` | 同上 |

**已知限制（必须写进报告，不能藏）**：仓库 6 笔交易里只有 **1 笔**能归到客户（其余 5 笔身份未解析 → `customer_key = NULL`）。
所以 R1 的 `amount_aud` 合计是 **980.75**，而仓库总额是 **1835.50**。这不是丢数据，见 R6。

### R2 / R2b 交易分析
- 事实：`fact_transaction`（粒度 = 1 笔已结算 S2 交易）。
- 维度：`dim_date`（`date_key = yyyymmdd`）、`dim_channel`。
- 口径：`txn_count = count(*)`，`amount_aud = sum(amount_aud)`；**不做去重**（每笔交易天然唯一，`transaction_id` 有 UNIQUE 约束）。
- **不含**：非 `SETTLED` 交易（fixture 中 `T0008` PENDING 被排除）、账户不存在于 S1 的交易（`T0007` → `rejected_record`）。

### R3 渠道参与 —— `dw.v_r3_channel_engagement`
- `active_customers` = 该渠道上**去重**的活动客户数（`count(DISTINCT customer_key)`）。
- `activity_count` = 该渠道的活动事件数（=1 每行求和）。
- 用 `dim_channel` **左连接**，所以没有活动的渠道显示 0（而不是从报表里消失）。
- ⚠️ **本视图刻意不含工单列**：源表 `s3_digital.service_cases` 没有渠道字段（T10a 实测 0 个渠道列）。
  早期版本用 `CROSS JOIN` 把工单总数摊到每个渠道行上（APP 和 WEB 都显示"工单 4"），
  那是**编造归属**，已删除 —— 见 `测试矩阵.md` §3 缺陷 8。

### R4 工单状态汇总 —— `dw.v_r4_service_case_summary`
- 粒度 = 状态（`OPEN` / `PENDING` / `CLOSED`）。
- `customers` = `count(DISTINCT customer_key)`；`PENDING` 显示 0 位客户，因为唯一一条 PENDING 工单（`SC003`）
  属于未匹配身份 `U003`（`customer_key = NULL`）——**这是真实结果，不是 bug**，报告里应当作数据质量例子讲。
- `high_severity` = `count(severity='HIGH')`。
